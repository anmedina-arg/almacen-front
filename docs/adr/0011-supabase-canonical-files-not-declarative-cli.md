# `supabase/`: un archivo canónico por objeto, agrupado por dominio — sin CLI declarativo

`supabase/` llegó a tener 47 archivos `.sql` sueltos en la raíz, cada uno un cambio histórico distinto (a veces varios objetos a la vez, a veces el mismo objeto redefinido en 5-6 archivos con el tiempo — `create_order()` es el caso extremo, ver #49). No había forma de saber, mirando el repo, cuál definición de un objeto era la vigente sin correr una query contra la base — eso causó dos incidentes de producción reales (#70: overload silencioso de `create_order`; una regresión de stock virtual de combos por basarse en el archivo más viejo). El mapa de decisiones #74 evaluó dos caminos para resolverlo.

**Opción A — adoptar el flujo declarativo `schemas/` + `migrations/` de la Supabase CLI** (`supabase db diff` genera migraciones comparando archivos de schema contra el historial, no contra la base viva). Investigado a fondo en #75 (ver `docs/research-supabase-declarative-schemas.md`, fuentes primarias). Combinados, tres hallazgos lo descalifican para adoptar *ahora* sin pinear versión: el motor de diff default cambió de `migra` a `pg-delta` hace pocos meses (alpha pública recién en abril 2026), `pg-delta` tiene un bug confirmado que hace invisibles los triggers sobre `auth.users` — un patrón que este repo ya usa (`on_auth_user_created`) — y `ALTER POLICY` no se captura en ningún motor, mientras que este repo altera policies existentes con frecuencia (ver el historial de `supabase_store_scoping_*.sql`). Ningún riesgo es descalificante por sí solo; combinados, sí.

**Opción B — disciplina manual "un archivo por objeto"**, sin CLI ni diffing automático: `supabase/schema/<dominio>/<objeto>.sql`, cada archivo verificado contra la base viva (`pg_get_functiondef`/`pg_policies`/`information_schema`) antes de escribirse — nunca contra el archivo más reciente por fecha. Ver el flujo completo en `docs/agents/schema-changes.md`.

Se optó por la Opción B. La automatización con CLI queda anotada como candidata futura, no descartada — si `pg-delta` madura (deja alpha, cubre `ALTER POLICY` y triggers en `auth.users`), vale reconsiderar. Hasta entonces, la disciplina de verificación manual es más barata que adoptar una herramienta con gaps documentados exactamente en los dos puntos que ya causaron incidentes reales en este repo (overload de función, regresión de policy).

**Consecuencias**: cada cambio de schema paga el costo de una verificación manual explícita (los 8 pasos de `schema-changes.md`) en vez de que una herramienta lo haga por vos — ese costo es intencional, es la mitigación del riesgo de Opción A. La reorganización completa (mapa #74, tickets #82-#90) tomó una sesión dedicada; agregar un dominio nuevo o un objeto nuevo a uno existente debería ser mucho más barato si se sigue la convención (ver la sección "Agregar un objeto o dominio nuevo" en `schema-changes.md`) — el costo alto fue de la migración inicial, no de mantenerla.
