# Orden de aplicación de los archivos canónicos para levantar el schema
# desde cero (base local en Docker, ver docs/ops/base-local-docker.md).
#
# Lo consume scripts/build-local-schema.mjs, que concatena estos archivos en
# una migración generada (supabase/migrations/, gitignoreada). Los archivos
# canónicos siguen siendo la única fuente de verdad del repo (ADR-0011);
# este manifiesto solo fija el orden, que importa por tres motivos:
#   - una tabla con FK necesita la tabla referenciada creada antes;
#   - una policy o un trigger necesita su función creada antes;
#   - una función LANGUAGE sql (is_store_admin, is_stock_tracked,
#     get_combo_effective_stock, get_top_seller_ids, get_recommendations)
#     se valida al crearse, así que necesita sus tablas antes. Las plpgsql
#     no (solo se validan al ejecutarse), pero `RETURNS product_stock`
#     exige que la tabla exista.
#
# Regla del build: TODO archivo .sql bajo supabase/schema/ tiene que estar
# listado acá — si falta uno, el build falla, para que un objeto nuevo no
# quede afuera de la base local en silencio.
